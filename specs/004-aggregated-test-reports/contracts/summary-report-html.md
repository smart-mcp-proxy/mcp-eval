# Contract: Summary Report HTML Output

**Feature**: 004-aggregated-test-reports
**Date**: 2025-11-11
**Contract Type**: HTML Document Structure

## Overview

This contract defines the structure and content requirements for aggregated summary HTML reports generated by `generate_summary_report()`. The HTML must be valid HTML5, render correctly in modern browsers (Chrome, Firefox, Safari), and contain specific data elements for each scenario.

## HTML Document Structure

###  Document Head

**Required Elements**:
```html
<!DOCTYPE html>
<html lang="en">
<head>
    <meta charset="UTF-8">
    <meta name="viewport" content="width=device-width, initial-scale=1.0">
    <title>MCP Evaluation Test Summary - [TIMESTAMP]</title>
    <style>
        /* Embedded CSS - see Style Contract section */
    </style>
</head>
```

**Constraints**:
- `charset` must be UTF-8 for Unicode scenario names
- `viewport` meta tag required for responsive rendering
- Title must include timestamp in human-readable format (e.g., "2025-11-11 14:31:47")
- All CSS must be embedded inline (no external stylesheets)

---

### Document Body Structure

```html
<body>
    <!-- Header Section -->
    <header>
        <h1>MCP Evaluation Test Summary</h1>
        <div class="summary-stats">
            <span class="stat">Total: [TOTAL]</span>
            <span class="stat passed">[PASSED] passed</span>
            <span class="stat failed">[FAILED] failed</span>
            <span class="stat recorded">[RECORDED] recorded</span>
            <!-- Optional: only show if error_count > 0 -->
            <span class="stat error">[ERROR] errors</span>
        </div>
        <div class="metadata">
            <span>Test Run: [TIMESTAMP ISO-8601]</span>
            <span>Git: [HASH]</span>  <!-- Optional: if available -->
            <span>Config: [PATH]</span>  <!-- Optional: if specified -->
        </div>
    </header>

    <!-- Results Table -->
    <main>
        <table class="scenarios-table">
            <thead>
                <tr>
                    <th>Scenario</th>
                    <th>Intent</th>
                    <th>Status</th>
                    <th>Tools</th>
                    <th>Duration</th>
                    <th>Score</th> <!-- Optional: hide column if all scores null -->
                </tr>
            </thead>
            <tbody>
                <!-- One row per scenario (see Row Contract section) -->
            </tbody>
        </table>
    </main>

    <!-- Footer -->
    <footer>
        <p>Generated by mcp-eval v[VERSION]</p>
    </footer>
</body>
</html>
```

**Constraints**:
- Header stats must show actual counts (not placeholders)
- Error stat span only included if `error_count > 0`
- Metadata fields optional based on data availability
- Table must have semantic `<thead>` and `<tbody>` for accessibility
- Score column hidden if all scenarios have `similarity_score=None`

---

### Table Row Contract

Each scenario must have exactly one `<tr>` in `<tbody>`:

```html
<tr class="scenario-row status-[STATUS_LOWERCASE]">
    <td class="scenario-name">
        <a href="[DETAILED_REPORT_PATH]">[SCENARIO_PATH]</a>
    </td>
    <td class="intent" title="[FULL_INTENT]">
        [TRUNCATED_INTENT]
    </td>
    <td class="status">
        <span class="badge status-[STATUS_LOWERCASE]">[STATUS]</span>
    </td>
    <td class="tool-count">[COUNT]</td>
    <td class="duration">[SECONDS]s</td>
    <td class="similarity-score">[SCORE or "N/A"]</td>
</tr>
```

**Field Requirements**:

1. **Scenario Name**:
   - Must be clickable hyperlink to detailed report
   - Link `href` attribute uses relative path (same directory)
   - Display text shows `scenario_path` (includes subdirectory if present)
   - Example: `<a href="add_simple_server_baseline_20251111_143147.html">tool_management/add_simple_server</a>`

2. **Intent**:
   - Display truncated version if >60 characters
   - Full intent shown in `title` attribute (tooltip on hover)
   - Truncation: `intent[:60] + "..."` if length >60
   - Example: `<td class="intent" title="Add a new MCP server called 'test-server' using Docker image 'mcp/fetch'">Add a new MCP server called 'test-server' using Docke...</td>`

3. **Status Badge**:
   - Nested `<span>` with two classes: `badge` and `status-[lowercase]`
   - Text content is uppercase enum value: "PASSED", "FAILED", "RECORDED", "ERROR"
   - CSS class determines background color (see Style Contract)
   - Example: `<span class="badge status-passed">PASSED</span>`

4. **Tool Count**:
   - Integer value with no formatting
   - Example: `<td class="tool-count">6</td>`

5. **Duration**:
   - Float rounded to 1 decimal place + "s" suffix
   - Example: `<td class="duration">23.5s</td>`

6. **Similarity Score**:
   - Float rounded to 2 decimal places (0.00-1.00) if present
   - "N/A" text if `similarity_score=None` (RECORDED status)
   - Example: `<td class="similarity-score">0.92</td>` or `<td class="similarity-score">N/A</td>`

**Row Ordering**:
- Scenarios displayed in execution order (order of `scenario_summaries` list)
- No client-side sorting applied by default (P3 feature)

## Style Contract (Embedded CSS)

**Color Palette** (from existing html_reporter.py):
```css
:root {
    --color-passed: #28a745;   /* Green */
    --color-failed: #dc3545;   /* Red */
    --color-recorded: #007bff; /* Blue */
    --color-error: #ffc107;    /* Yellow */
    --color-bg: #ffffff;       /* White background */
    --color-text: #212529;     /* Dark gray text */
    --color-border: #dee2e6;   /* Light gray borders */
}
```

**Required CSS Classes**:

1. **Status Badge Styles**:
```css
.badge {
    display: inline-block;
    padding: 4px 8px;
    border-radius: 4px;
    font-size: 0.875rem;
    font-weight: 600;
    color: white;
    text-align: center;
}

.status-passed { background-color: var(--color-passed); }
.status-failed { background-color: var(--color-failed); }
.status-recorded { background-color: var(--color-recorded); }
.status-error { background-color: var(--color-error); color: #212529; } /* Dark text on yellow */
```

2. **Table Styles**:
```css
.scenarios-table {
    width: 100%;
    border-collapse: collapse;
    margin-top: 20px;
}

.scenarios-table thead {
    background-color: #f8f9fa;
    border-bottom: 2px solid var(--color-border);
}

.scenarios-table th {
    padding: 12px;
    text-align: left;
    font-weight: 600;
    color: var(--color-text);
}

.scenarios-table td {
    padding: 10px 12px;
    border-bottom: 1px solid var(--color-border);
}

.scenarios-table tbody tr:hover {
    background-color: #f8f9fa;
}
```

3. **Responsive Wrapper**:
```css
main {
    overflow-x: auto; /* Horizontal scroll for narrow viewports */
}

.intent {
    max-width: 300px;
    overflow: hidden;
    text-overflow: ellipsis;
    white-space: nowrap;
}
```

**Accessibility Requirements**:
- Color contrast ratio ≥4.5:1 for text (WCAG AA)
- White text on green/red/blue passes WCAG AA
- Dark text on yellow (ERROR) required for contrast
- Hover states for interactive elements
- Semantic HTML (thead, tbody, th scope)

## Validation Requirements

### HTML Validity
- Document must pass W3C HTML5 validator
- All tags properly closed
- Attributes quoted
- Valid entity encoding for special characters

### Content Completeness
1. **Header Stats**: All counts present and accurate
   - `passed_count + failed_count + recorded_count + error_count == total_scenarios`
2. **Table Rows**: Exactly `total_scenarios` rows in tbody
3. **Links**: All scenario name links point to existing report files
4. **Badges**: All status badges have correct class and color

### Browser Compatibility
- Renders correctly in Chrome 90+, Firefox 88+, Safari 14+
- CSS Grid/Flexbox for layout (modern browser features)
- No vendor prefixes required for target browser versions
- JavaScript optional (P3 feature) - table fully functional without JS

## Testing Contract

### Unit Test Requirements

1. **Test HTML Structure**:
   - Verify doctype, charset, viewport meta tags
   - Confirm all required sections present (header, main, footer)
   - Check table has thead and tbody

2. **Test Content Accuracy**:
   - Header stats match input `TestRunSummary` counts
   - Table row count equals `total_scenarios`
   - Each row contains all required cells

3. **Test Link Correctness**:
   - Scenario name links use relative paths
   - Links match `detailed_report_path` from input data
   - Links end with ".html" extension

4. **Test Status Badges**:
   - Correct CSS class for each status
   - Badge text matches enum value (uppercase)
   - All four status types covered (PASSED, FAILED, RECORDED, ERROR)

5. **Test Truncation**:
   - Intents >60 chars show "..." suffix
   - Full intent available in title attribute
   - Intents ≤60 chars not truncated

6. **Test Edge Cases**:
   - Zero tools (tool_count=0) displays "0"
   - Null similarity score displays "N/A"
   - Empty intent string displays as empty cell
   - Very long scenario names (100+ chars) don't break layout

### Integration Test Requirements

1. **End-to-End Test**:
   - Run `mcp-eval test --scenarios-dir scenarios/` with 5+ scenarios
   - Verify summary HTML file generated in reports/
   - Open in browser, confirm rendering
   - Click scenario links, verify navigation to detailed reports

2. **Multi-Status Test**:
   - Create test run with PASSED, FAILED, RECORDED, ERROR scenarios
   - Verify all status colors display correctly
   - Confirm error stat only shown when error_count >0

3. **Cross-Browser Test**:
   - Open generated HTML in Chrome, Firefox, Safari
   - Verify table renders identically
   - Test hover states work on all browsers
   - Confirm responsive behavior on narrow viewports (mobile)

## Versioning

**Contract Version**: 1.0.0
**Breaking Changes**: Any modification to:
- Required HTML element structure
- CSS class names used by external tools
- Link format or path resolution
- Table column order

**Non-Breaking Changes**:
- Additional optional metadata fields
- CSS styling improvements
- New optional columns (if hidden by default)
- Performance optimizations

**Backward Compatibility**: This is the initial version, no compatibility requirements yet. Future versions must support reading old-format detailed_log.json files to generate summary reports.
